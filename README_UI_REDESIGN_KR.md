# AI 기반 의사결정 대시보드 UI 리디자인

## 참고한 제품 UI 원칙

- Linear: 업무 흐름을 방해하는 요소를 줄이고, 현재 작업과 상태를 빠르게 파악하는 탐색 구조
- Notion 프로젝트 대시보드: 문서·상태·담당·진행 정보를 한 화면에서 연결해 보는 단일 작업공간
- Jira Product Discovery: 평가기준, 우선순위, 진행 상태를 구조화해 의사결정 근거를 함께 표시
- Miro Decision Matrix: 대안과 기준을 비교 가능한 시각 구조로 표현

특정 제품 화면을 복제하지 않고 위 원칙을 현재 Project Zero 구조에 맞게 재해석했습니다.

## 주요 변경

1. 편집 화면 좌측에 고정 작업공간 내비게이션 추가
2. 현재 문서명, 작성자, 준비도, 현재 단계, DB 상태를 사이드바에 표시
3. 안건 입력·5대 요소·STAGE 01~04·최종 보고서로 즉시 이동
4. 홈 화면을 넓은 대시보드형 레이아웃으로 변경
5. 문서 카드를 2열 중심으로 확장해 제목과 메타데이터 가독성 개선
6. 설정·위임 수준·안건·단계·보고서를 동일한 카드 규칙으로 통일
7. 검은색 대형 블록을 줄이고 밝은 중립 배경과 명확한 강조색 적용
8. 제목 서체와 본문 서체를 정리하고 문장 폭·행간·여백 체계 통일
9. 모바일에서는 사이드바를 슬라이드 메뉴로 전환
10. 기존 DB, AI, 저장, 이력, 초기화, 삭제 기능은 유지

## 배포

기존 저장소에 전체 파일을 덮어쓸 수 있습니다. UI 변경의 핵심 파일은 `index.html`입니다.
백엔드 기능 변경은 없으므로 기존 Render 배포가 정상이라면 UI 적용만을 위해 재배포할 필요는 없습니다.


## Workflow 입력 상태 및 STAGE 산출 요약·팝업 편집

### Workflow 입력 상태

좌측 WORKFLOW 메뉴와 상단 STAGE 파이프라인에 다음 상태를 표시합니다.

- `입력`: 해당 단계의 입력값, 첨부자료 또는 AI 산출 결과가 존재
- `미입력`: 해당 단계에 입력·산출 데이터가 없음

상태는 안건·회의 메모·진행 현황 입력, 파일 첨부, AI 산출, 문서 불러오기,
STAGE 초기화 시 자동 갱신됩니다.

### STAGE 01~04 결과 표시

기존처럼 카드에 전체 본문을 노출하지 않고 다음 내용만 표시합니다.

- 핵심 결론
- 핵심 요약
- 최종 결론
- 종합 진단
- 각 항목의 첫 번째 핵심 근거

카드에는 최대 4줄의 요약만 표시되며 `전체 보기 · 수정` 안내가 추가됩니다.

### 상세 팝업과 수정

STAGE 결과 카드를 클릭하면 다음 기능을 제공하는 팝업이 열립니다.

- 전체 산출 본문 확인
- 전체 내용을 텍스트 영역에서 직접 수정
- STAGE 01 검증 출처 확인
- 수정 내용을 공유 DB에 새로운 산출 이력으로 저장
- 기존 이력 보존
- 문서 재조회 시 가장 최근 수정 이력 자동 복원

수정 저장은 기존 PostgreSQL `decision_history` 구조를 사용하므로
Neon DB 스키마 변경은 필요하지 않습니다.


## Google Search 근거 조회 혼잡 개선

`대체 모델로 근거 조회 처리 중`은 기본 모델이 429·503·시간 초과 등
일시적 오류를 반환해 자동 복구 로직이 다른 지원 모델로 전환된 상태입니다.

개선 사항:

- 일반 분석과 근거 조회의 모델 정책 분리
- 근거 조회는 `gemini-2.5-flash-lite`를 우선 사용
- 근거 조회 자동 시도 횟수 5회 → 3회
- 상태 문구를 `근거 조회 최적화 모델`, `근거 조회 모델 자동 전환`으로 변경
- 분석 전체 대신 핵심 주장·수치 중심 약 1,100자만 검색 검증에 전달
- 카테고리별 가장 직접적인 원문 1개만 요청
- Grounding thinking budget 0 적용
- 동일 안건·동일 분석의 검증 근거를 최대 12시간 캐시
- 일부 근거만 캐시된 경우 누락된 항목만 조회
- 근거 조회 실패 시에도 본문 분석 결과는 유지

프론트엔드 변경이므로 Render와 Neon DB 변경은 필요하지 않습니다.


## 회의 준비 자동 산출 서비스 혼잡 복구 순서 개선

회의 준비 버튼 실행 과정에서 적용되는 Gemini 모델 순서를 다음과 같이 변경했습니다.

```text
1차  Gemini 2.5 Flash 실행
2차  Gemini 2.5 Flash-Lite 실행
3차  Flash-Lite 자동 재시도 1/2
4차  Flash-Lite 자동 재시도 2/2
5차  필요할 때 Gemini 2.5 Flash 최종 전환
```

적용 범위:

- 회의 준비 실행 시 자동 작성되는 5대 핵심요소 1~3번 초안
- STAGE 01 회의 준비 본 분석

추가 개선:

- 첫 Flash 실패 후 Flash를 반복 호출하지 않고 즉시 Flash-Lite로 전환
- Flash-Lite에서 최대 2회만 재시도
- 마지막 복구 단계에서 Flash를 한 번 더 사용
- 최대 백오프 시간을 5초 수준으로 제한하여 불필요한 장시간 대기 감소
- 진행 상태를 모델과 시도 순서별로 명확하게 표시
- 회의 준비 버튼을 처리 중 비활성화하여 중복 클릭·중복 API 요청 방지
- 최종 실패 시 입력한 안건과 첨부자료는 유지

Google Search 근거 조회는 기존의 Flash-Lite 우선 정책과 12시간 캐시를 계속 사용합니다.
프론트엔드 변경이므로 Render와 Neon DB 변경은 필요하지 않습니다.


## 핵심요소 설계 번호 및 Gemini 429 오류 개선

- 좌측 메뉴 `핵심요소 설계` 번호를 `05`에서 `02`로 변경했습니다.
- 캡처의 실패는 503 서비스 혼잡이 아니라 HTTP 429 무료 API 요청 한도 초과입니다.
- 오류 메시지에서 약 59초 후 재시도를 안내했지만 기존 코드는 최대 30초만 기다려 너무 일찍 재호출했습니다.
- STAGE 01, 03, 04에서 핵심요소 초안과 본 분석을 따로 호출하던 구조를 하나의 응답으로 통합했습니다.
- 각 STAGE 버튼의 기본 생성 API 호출을 1회로 줄였습니다.
- 일반 분석 복구 순서를 `Flash → Flash-Lite → Flash-Lite 1회 재시도`로 변경했습니다.
- 모든 Gemini 호출을 직렬화하고 최소 3.5초 간격을 적용했습니다.
- Retry-After를 최대 120초까지 실제 안내값대로 반영합니다.
- 429 요청 한도, 503 서비스 혼잡, 시간 초과를 구분해 짧은 한국어 안내만 표시합니다.
- 긴 Google 오류 전문과 URL은 사용자 화면에 노출하지 않습니다.
- 오류 발생 후에도 입력 데이터는 유지됩니다.

프론트엔드 변경이므로 Render 및 Neon DB 변경은 필요하지 않습니다.


## STAGE 03 신뢰도·시간축 검증 강화

STAGE 03에서 현재 시점과 맞지 않는 과거 연도 또는 입력 근거가 없는 절대일정이
생성되는 문제를 개선했습니다.

- 브라우저의 현재 날짜를 기준일로 사용
- 안건, STAGE 01·02, 5대 핵심요소에서 실제 입력된 날짜만 추출
- 입력에 없는 절대 연도·월·분기 생성 금지
- 확정일이 없으면 승인일(T+0) 기준 상대일정 사용
- 기준일 이전 날짜는 마일스톤에서 자동 제외
- 과거 또는 입력 근거가 없는 날짜는 T+ 일정으로 자동 정규화
- 입력 근거가 없는 KPI·담당조직·Plan B는 제안값·확정 필요로 표시
- 결과에 신뢰도 점수와 검증 내역을 표시하는 별도 카드 추가

기존 PostgreSQL 구조를 그대로 사용하므로 Render와 Neon DB 변경은 필요하지 않습니다.


## STAGE 03 ROLE 정합성 강화

STAGE 03의 모든 결과가 다음 역할에만 집중하도록 로직을 재구성했습니다.

```text
STAGE 01·02 산출물을 바탕으로
최종 의사결정 요약, 담당자·R&R, 실행 일정,
관리 KPI, 후속 회의 Agenda를 자동 생성
```

### 실행 조건

- STAGE 01과 STAGE 02 산출물이 모두 있어야 STAGE 03 실행 가능
- STAGE 02만 존재하는 상태에서는 실행하지 않음

### 항목별 근거 매핑

- 최종 의사결정: STAGE 02 회의요약·대안평가
- 실행 전제·제약: STAGE 01 리스크·투자분석 + STAGE 02 대안평가
- 담당자·R&R: STAGE 02 Action Item
- 실행 일정: STAGE 02 Action Item + STAGE 01 리스크·제약
- 관리 KPI: STAGE 01 지표 + STAGE 02 평가기준·Action Item
- 리스크 대응 조건: STAGE 01 리스크 + STAGE 02 우려·이견
- 후속 회의 Agenda: STAGE 02 쟁점·미확정 사항

### 생성 후 로컬 검증

AI 응답을 그대로 사용하지 않고 다음을 다시 검사합니다.

- STAGE 02에 명시적 결정이 없으면 `최종 의사결정 미확정`으로 변경
- Action Item에 담당자가 없으면 `담당자·R&R 미확정`으로 변경
- 확정 KPI 근거가 없으면 제안 KPI와 `목표값 확정 필요`로 변경
- 쟁점과 미확정 담당자·일정·KPI를 후속 회의 Agenda로 자동 구성
- 각 카드 전체 내용에 실제 산출 근거를 추가
- 입력에 없는 조직명·수치·날짜는 확정값으로 사용하지 않음

### 역할 적합성 검증

기존 신뢰도 카드가 `산출 근거·역할 적합성` 카드로 강화됩니다.

- 최종 결정 근거 여부
- 담당자·R&R 근거 여부
- 일정 근거 및 T+ 정규화 여부
- KPI 근거 또는 제안값 처리 여부
- 후속 Agenda 생성 여부
- STAGE 03 ROLE 적합성 점수

별도 AI 검증 호출을 추가하지 않으므로 Gemini API 사용량은 증가하지 않습니다.
기존 PostgreSQL 구조를 그대로 사용하며 Render 및 Neon DB 변경은 필요하지 않습니다.


## 정확도 우선 분석 및 출처 검증 오류 개선

### 원인

화면에 표시된 오류는 `HTTP 429 RESOURCE_EXHAUSTED`입니다.

```text
generate_content_free_tier_requests
limit: 20
model: gemini-2.5-flash
retry: 약 56초
```

이는 Google Search 원문 검증 자체의 내용 오류가 아니라 Gemini 프로젝트의
무료 API 요청 한도를 초과한 상태입니다. 기존 로직은 429 이후에도
`보완 재검색`을 즉시 실행하여 동일한 429를 다시 발생시켰고, 해당 영문 오류를
`VERIFIED SOURCE` 영역에 그대로 표시했습니다.

### 수정 사항

- 429 요청 한도 발생 시 동일 실행에서 보완 재검색 중단
- API가 안내한 재시도 시간만 한국어로 표시
- 긴 영문 오류, URL, quota 원문을 화면과 DB에 저장하지 않음
- 503 서비스 혼잡과 429 요청 한도를 구분
- 검증 실패를 `VERIFIED SOURCE`로 표시하지 않음
- 검증 성공: `VERIFIED SOURCE · 실제 원문 참조`
- 429·503: `SOURCE VERIFICATION PENDING · 출처 검증 보류`
- 원문 미발견: `SOURCE NOT VERIFIED · 실제 원문 미확인`
- 성공한 실제 원문만 12시간 캐시에 저장

### 정확도 우선 생성

STAGE 01 분석은 다음 정책을 사용합니다.

- 사용자 입력·첨부자료·5대 핵심요소만 사실 근거로 사용
- 입력에 없는 기업명·시장규모·성장률·투자금·연도·사례 생성 금지
- 구체적 숫자는 입력에 동일한 숫자가 있을 때만 사용
- 경쟁사·시장규모·투자 데이터가 없으면 `확인 불가`로 처리
- 사실, 분석 가설, 추가 확인 항목을 구분
- 생성 온도를 0.05로 낮추고 단일 후보만 생성
- 생성 후 입력에 없는 수치·연도·비율을 로컬 코드가 다시 제거

### 정확도·출처 검증 카드

STAGE 01 결과에 다음 내용을 표시하는 별도 카드가 추가됩니다.

- 입력 근거 우선 정책 적용 여부
- 실제 원문 연결 완료 건수
- 검증 보류 항목 수
- API 요청 한도로 보류된 항목 수
- 입력 근거에 없어 제거한 수치·연도·비율 건수
- 미검증 분석을 확정 근거로 사용하지 말라는 안내

기존 PostgreSQL 구조를 그대로 사용하므로 Render와 Neon DB 변경은 필요하지 않습니다.
